# Спецификация разработки: стандартизация заявок XLSX

Версия: **1.7**. Дата: **2026-10-08**, Europe/Moscow.

Документ объединяет требования, решения, алгоритмы, контракт CLI, структуру результата,
сценарии проверки, архитектуру и план разработки. Реализованы предварительный генератор,
обработчик `normalize.py` и побайтное восстановление `restore.py`. Версия 1.4 вводит
пять листов, строгий допуск в «Данные» и подтверждённый запасной порядок даты.
Версия 1.5 добавляет согласованный пробельный разделитель числовой даты и уточняет
границы повреждённых телефонных кандидатов. Команды ниже исполняются из корня проекта;
инструкция и результаты проверок — README.md.

Версия 1.6 добавляет DEC-29: подтверждённое имя из ФИО с «Петрович» можно извлечь,
сохранив NAME_AMBIGUOUS и направив всю заявку на проверку. Проверки версии 1.5
остаются историческими; новые доказательства описаны в FORMAL_VERIFICATION_REPORT.md.

Версия 1.7 вводит согласование группы дублей по DEC-30–34. Правила 1.6 о запрете
дополнения полей и исключении конфликтов из «Данных» заменены этими решениями.
Исторические свидетельства 1.6 доказывают только прежний контракт.

## 1. Основание и границы

Основание: `files/task.txt`, сверенный с одностраничным `files/task.pdf`, исходное сообщение
заказчика и его ответы в этой сессии. В `files/` нет `zayavki.xlsx`; 48 строк и сентябрь 2026
из легенды не являются ограничением алгоритма. Примеры заказчика, включая май и март,
имеют приоритет над легендой.

Цель: CLI-программа на Python получает XLSX с колонками **Имя, Телефон, Дата заявки, Источник**,
создаёт **один новый XLSX** с пятью листами и сохраняет всю исходную информацию.
Проблемы доступны отдельным списком внутри этого же файла.

Автоматическое изменение разрешено только при однозначном соответствии правилам этого документа.
Неподдерживаемое или неоднозначное значение сохраняется буквально и требует ручного рассмотрения.
Нельзя гарантировать распознавание любой произвольной строки: гарантия распространяется на
перечисленные классы форматов, сохранение входа и явную диагностику всего остального.

AI используется при разработке. В рабочем конвейере нет LLM, внешних запросов, словарного
угадывания имён, SMS-проверок и ручной подготовки файла. Формат телефона не подтверждает
существование номера или принадлежность человеку. Для этой задачи один одинаковый
нормализованный телефон считается одним человеком по правилу заказчика.

Нормативные технические правила ниже фиксируются до реализации обработчика. Если разработчик
находит новый формат, он сначала добавляет правило, пример и ожидаемый результат в новую версию
документа и каталога. Изменения ключевых правил DEC-01–08 и DEC-12–16 согласуются с заказчиком; разработчик
не вправе менять представителя на «самую полную», дополнять значения вне DEC-31 или менять DMY.
Локальные рефакторинги при сохранении контракта не требуют новой бизнес-логики.

Журнал решений — этот раздел. История общения с AI — отдельный обязательный артефакт финальной
сдачи по заданию, её нельзя подменять кратким журналом решений или выдуманным отчётом.
Полную историю экспортирует пользователь из своей среды; текущий комплект не утверждает,
что такой экспорт уже получен. Разрешено скрыть только перечисленные в исходном задании секреты.

## 4. Входной контракт XLSX

Принимается обычный читаемый `.xlsx`, соответствующий OOXML. CSV, XLS, XLSM, зашифрованный,
повреждённый архив и файл другого типа с расширением `.xlsx` — ошибка входа. Исходник открывается
для чтения; его SHA-256 вычисляется по тем же байтам, которые архивируются и разбираются.
Нельзя сначала прочитать файл, а затем встроить другую его версию при параллельном изменении.

Заголовок расположен в первой строке. Для сопоставления заголовков разрешено удалить только
краевые Unicode-пробелы; регистр и написание названий должны совпадать. Колонки могут идти
в другом порядке: сопоставление по именам однозначно; результат всегда в заданном порядке.
Каждый заголовок встречается один раз. Отсутствие, повтор, лишняя заполненная колонка или
данные вне четырёх соответствующих колонок — `SCHEMA_INVALID`, без частичного результата.
Колонки, существующие только из-за оформления, не считаются дополнительными данными.

Если `--sheet` указан, обрабатывается этот лист. Иначе программа выбирает единственный лист
с подходящей схемой; ноль подходящих листов — `SCHEMA_INVALID`, несколько — `SHEET_AMBIGUOUS`.
Остальные листы побайтно сохраняются во встроенном исходнике, но не смешиваются с заявками.
Скрытые строки и строки, скрытые фильтром, выбранного листа обрабатываются наравне с видимыми.

Диапазон заявок: строки 2…последняя строка, содержащая значение/формулу/ошибку в четырёх колонках.
OOXML `dimension` и `max_row` не являются доказательством полноты: читать фактические
ячейки XML, а при потоковом чтении сбрасывать недостоверные размеры листа. Нельзя
успешно завершить обработку с усечёнными данными из-за `dimension="A1:A1"`.
Перед обработкой отклонять контейнер с повторяющимися именами ZIP-частей, ошибкой CRC
или отсутствующим/повреждённым обязательным содержимым XLSX (`INPUT_INVALID`).
Флаг шифрования ZIP в центральном либо локальном заголовке означает неподдерживаемую
книгу: INPUT_INVALID, без публикации. Несогласованные заголовки не дают права обойти
этот отказ. Проверка не выполняет распаковку за установленными пределами контейнера.
Повреждение при чтении последних строк также запрещает публикацию частичного результата.
Пустые строки **внутри** диапазона — отдельные записи с пропусками; они сохраняются
в Проблемах, Оригинале, Аудите и Проверить, но не допускаются в Данные по DEC-22.
Хвост из пустых оформленных строк не считается заявками, но сохраняется в исходнике.
Книга только с заголовком допустима: ноль записей, все пять выходных листов созданы.
Полностью пустая книга — ошибка схемы.

Объединённые ячейки, пересекающие заголовок или диапазон записей, — `MERGED_INPUT`:
не размножать имя/телефон по строкам. Необъединённые многострочные текстовые ячейки допустимы.
Повтор заголовка внутри диапазона считается обычной проблемной строкой, не удаляется молча.

Типы ячеек сохраняются в модели. Числа, строки, даты, bool, формулы и Excel-ошибки не смешиваются.
`True` не является числом телефона. Не использовать `astype(str)` / общий числовой cast для таблицы.
Формулы читаются с `data_only=False`; вычисление и доверие устаревшему кэшу запрещены.
Даже `=DATE(...)` или `=CONCAT(...)` остаётся исходной формулой с `FIELD_FORMULA`.
Excel-ошибка в любой колонке — `FIELD_EXCEL_ERROR`; строка `#N/A` не является Excel-ошибкой,
если тип ячейки строковый.
Числовое NaN/Infinity в XML сохраняется как исходная числовая лексема текстом и
CELL_NUMERIC_INVALID в соответствующем поле. В metadata остаётся исходный тип n/XML;
читатель использует изолированную рабочую копию с временным конечным числом только для
чтения openpyxl. Исходные байты/архив и raw не заменяются рабочей копией. В «Данные» такая
заявка не попадает. Другие повреждения числа/структуры не чинятся догадкой.

## 5. Общие правила поля

Результат каждого анализатора: `raw`, `canonical` (или `null`), `display_value`, `status`,
`codes`, `diagnostic_codes`, `actions`. Статус: NORMALIZED / UNCHANGED / MISSING / PROBLEM.
Отдельная диагностика не означает провал извлечения: успешный телефон может иметь
PHONE_EXTRA_CONTEXT, ненулевой canonical и статус NORMALIZED. Любой код создаёт запись в Проблемах;
severity (error/diagnostic) и причина остаются явными. Нельзя вычислять успех как `not codes`.
Для успешного преобразования `display_value = canonical`; для отказа преобразования `display_value = raw`.
Для имени, требующего проверки регистра/латиницы, display остаётся raw; ключ сравнения отдельно проходит NFC.
`null` в canonical не означает разрешения стереть raw. Анализаторы не меняют соседние поля.
В проблемной строке корректно распознанные поля всё равно стандартизируются.

Для обязательных полей пустотой считаются: отсутствующее значение, строка только из Unicode-пробелов
или полное совпадение после trim/casefold с одним из токенов:
`-`, `—`, `нет`, `неизвестно`, `не указано`, `n/a`, `null`, `none`, `nan`.
Никакие подстроки не заменяются: например, фамилия «Нетов» не пустота.
Исходные маркеры сохраняются буквально. Для Источника эти токены не интерпретируются.

Unicode-нормализация не должна создавать неизвестные цифры или стирать невидимые символы.
Для телефона и числовой части текстовой даты Unicode-категория `Nd` может однозначно преобразовываться
через `unicodedata.decimal` в ASCII. Полноширинный `＋` эквивалентен `+` в телефоне.
Остальные символы, включая `⑨`, не становятся цифрами через NFKC или `isdigit()`.
Zero-width space внутри значения не считается разрешённым телефонным разделителем.

## 6. Телефон: распознавание и нормализация

### 6.1 Принятые формы

| Цифры кандидата | Преобразование |
|---|---|
| 10 цифр без явного международного `+` | Приписать `+7` |
| 11 цифр, первая 8, без `+` | Заменить 8 на `+7` |
| 11 цифр, первая 7, без `+` | Приписать `+` |
| `+7` и 10 цифр | Удалить разрешённые разделители |
| Другой `+код`, включая `+8` | Сохранить; `PHONE_UNSUPPORTED_PREFIX` |
| `00…`, `810…`, даже при 10/11 цифрах | Не интерпретировать префикс; PHONE_UNSUPPORTED_PREFIX (DEC-21) |

Распознавание структурное: мобильные, городские, 800 и другие 10-значные национальные номера
принимаются одинаково. `+70000000000` удовлетворяет согласованной структуре; это не утверждение
о реальном назначении. Нельзя добавлять региональный код к короткому местному номеру.

### 6.2 Границы кандидатов — важнее удаления символов

Запрещён алгоритм `re.sub(r"\D", "", entire_cell)`: он склеивает телефон, время, добавочный,
номер заказа и несколько телефонов. Цифры извлекаются **в пределах одного кандидата**.

1. Обработать тип, формулу, Excel-ошибку и пропуск. Числовой телефон допускается, если
   значение конечное, неотрицательное, целое и точно представимо (`abs(value) <= 2**53 - 1`
   для float). Значение `89174005219.0` допустимо как число; текст с `.0` не считается числом.
   Научный формат отображения целой числовой ячейки не мешает; текст `8.9174005219E10` не парсится.
2. В рабочей копии преобразовать `Nd` и полноширинный плюс. Raw оставить нетронутым.
3. Выделить известные комментарии **после** номера: `(после HH:MM)`, `после HH:MM`,
   `звонить после HH:MM`, `(с H до H)`. H — 0…23, MM — 00…59. Скобки комментария
   относятся к комментарию, не к телефонной группе. Цифры комментария не участвуют в номере.
   Некорректное время или числовой комментарий неизвестного вида не отбрасывается автоматически.
4. Выделить помеченный добавочный после номера: `доб.`, `доб`, `добавочный`, `ext.`, `ext`,
   `extension`, `#`, `вн.`, `доп.`, `*`, `;ext=`, а также отдельный `x`/`х` перед добавочным вне основного номера.
   Простой добавочный (1…6 цифр), список или дефисная запись после явного маркера допускают
   извлечение основного номера, если его границы и единственность гарантированы.
   Значения `10-17, 10-13` не преобразуются ни в `10`, ни в `1017`: весь хвост хранится буквально.
   Основной телефон стандартизируется; дополнительный контекст сохраняется в Оригинале,
   аудите PHONE_CONTEXT_EXTRACTED и Проблемах с PHONE_EXTRA_CONTEXT.
   Если хвост содержит другой полный номер или повреждённый фрагмент вне распознанного контекста,
   однозначность потеряна: обычные PHONE_MULTIPLE/PHONE_INVALID, без выбора первого номера.
   Комбинация известного времени и добавочного также допускается с сохранением всего контекста.
   `89174005219 123` без маркера нельзя обрезать; добавочный перед телефоном не интерпретируется.
5. Из оставшегося текста выделить максимальные телефонные последовательности. Внутри допустимы
   Unicode-пробелы (включая таб/перенос/NBSP), ASCII `-`, `.`, Unicode-дефисы `‐‑‒–—−` и парные
   круглые скобки. Плюс допустим один раз в начале. Скобки кандидата сбалансированы, не вложены,
   охватывают непустую цифровую группу. Цифровые группы соединяются только этими разделителями.
   `/`, `;`, `,` разделяют кандидаты и не склеиваются. Каждый кандидат проверяется целиком;
   нельзя взять первые/последние 10–11 цифр из длинного числового блока или разбить его по догадке.
6. Не извлекать кандидат, примыкающий к букве: `abc89174005219xyz` и `8a9174005219` — проблема.
   Числовые буквенные токены, остаточные цифры вне разрешённых комментариев/добавочного и
   повреждённые фрагменты номера запрещают «спасать» соседний фрагмент. Явные маркеры чужих
   идентификаторов (`заказ`, `order`, `id`, `ИНН`, `ОГРН`, `паспорт`, `счёт`, `счет`) перед кандидатом
   дают `PHONE_CONTEXT_UNSAFE`. Метки `тел`, `тел.`, `тел.:`, `телефон`, `номер`, `tel`, `tel:`
   разрешены. Произвольный текст без других цифр допустим, если кандидат отделён границами и нет
   перечисленных конфликтов. Контекст и исходный текст сохраняются в аудите и Проблемах.
   Метка `тел.:`, текстовый комментарий, время или добавочный вне кандидата дают PHONE_EXTRA_CONTEXT;
   телефонные разделители и форматирование внутри кандидата не являются дополнительным контекстом.
7. Проверить каждый полный кандидат на длину и префикс. Внешние границы списка и комментариев
   разрешают извлечение `тел.: 8 917 400 52 19 (после 18:00)` без цифр `1800`.
   Связку нескольких номеров без ясного разделителя, например `+79174005219 +79174005220`,
   распознавать как несколько кандидатов по второму явному `+`, а не склеивать.
8. Несколько записей **одного** нормализованного номера допустимы. Несколько разных полных
   номеров, в том числе смесь +7 и иностранного, — `PHONE_MULTIPLE`: не выбирать первый.
   Если есть один хороший номер и ещё повреждённый цифровой фрагмент, поле проблемное
   (`PHONE_INVALID` либо `PHONE_CONTEXT_UNSAFE`), не объявлять его однозначным.
   Маркер добавочного не даёт права скрыть полный телефон: каждую часть хвоста между
   `,`/`;` сначала проверять целиком как телефон, включая дефисную группировку.
   Хвост с 10/11 цифрами не скрывать как добавочный и при неправильном/запрещённом
   префиксе: его структурная ошибка должна остаться проблемой поля.
   Разные полные номера дают PHONE_MULTIPLE, одинаковые считаются повтором по п.8;
   пустой/буквенный или иной повреждённый хвост маркера — PHONE_INVALID.
9. Единственный однозначный кандидат преобразовать по таблице; проверить итоговую регулярку.

Внешний видимый символ (`📞`, `；` и т.п.) не становится телефонным префиксом и не
превращается в ASCII через NFKC: если он вне целого однозначного кандидата, это
PHONE_EXTRA_CONTEXT с сохранением raw. Внутри цифровой последовательности такой символ
не является разрешённым разделителем: PHONE_INVALID. Unicode-категории Mn/Mc/Me
(включая variation selectors и keycap) непосредственно перед/после цифры либо плюса
создают повреждённую цифровую запись: PHONE_INVALID; не удалять их и не «спасать» цифры.
Знаки в явно отделённом внешнем текстовом контексте не запрещают целый номер.
Категории marks отличаются от управляющих Cc и форматирующих Cf.
Фрагмент после повреждающего символа не является новым телефонным префиксом:
`89174📞005219` — PHONE_INVALID, а не PHONE_UNSUPPORTED_PREFIX. Настоящие отдельные
`00…`/`810…` и явный иностранный `+код` сохраняют согласованный приоритет.

Приоритет единственного основного кода: `FIELD_*` → `PHONE_MISSING` → `PHONE_MULTIPLE` →
`PHONE_CONTEXT_UNSAFE` → `PHONE_UNSUPPORTED_PREFIX` → `PHONE_INVALID`. Для явного иностранного
`+кода` диагноз неподдерживаемого префикса приоритетнее букв в его хвосте.
Ни O/О→0, ни l/I→1, ни телефонная keypad-конверсия букв не разрешены.

дата заявки — календарная дата, записанная в ячейке; время и зона остаются в исходнике и аудите.

### 7.2 Проверка календаря и Excel

После разбора компонентов вызвать **`datetime.date(year, month, day)`**. `ValueError` —
`DATE_INVALID`, без переноса на следующий месяц, угадывания века или исправления букв.
Установленный диапазон года 1…9999, как у Python. Выход форматировать
`f"{year:04d}-{month:02d}-{day:02d}"`, не полагаться на платформенное дополнение года `strftime`.
Результат записывается в XLSX как текст, поэтому историческая корректная дата не зависит от Excel.

Числовая дата допустима только при подтверждённом датовом формате ячейки, содержащем
все календарные компоненты: число дня (d/dd), месяц (m…mmmmm), год (y…yyyy), вне
кавычек, экранированных литералов и служебных скобок. Форматы mm, yyyy, dd, dd.mm,
mmm yyyy и только день недели ddd/dddd — DATE_INCOMPLETE. Только время/длительность
также не доказывает дату. Проверяется действующая первая секция формата числовой даты.
Только `m`/`mm` после `h` или перед `s` означают минуты, а не месяц: dd yyyy hh:mm и dd yyyy mm:ss
не доказывают наличие месяца и дают DATE_INCOMPLETE.
Использовать `workbook.epoch`, `openpyxl.utils.datetime.from_excel` и проверку календаря;
учитывать 1900/1904, дробную часть суток и допустимые границы. Serial 0 в 1904 допустим
как 1904-01-01 при датовом формате, хотя высокоуровневый reader может вернуть time.
В системе 1900 serial 0 и отрицательные serial не трактуются как гарантированная дата;
в системе 1904 отрицательные serial также проблемные. Serial 60…60.999… в 1900 представляет
несуществующее 1900-02-29: `DATE_INVALID`, не 1900-02-28. В 1904 serial 60 = 1904-03-01.
Календарный день serial определяется целой частью: округление дробных суток библиотекой
не должно переносить дату на следующий день. Дробная часть сохраняется в аудите буквально.

Нужен выборочный разбор исходного XML `sheet*.xml` для числового значения ячейки, типа и style
**до** автоматического преобразования openpyxl: иначе serial 59 и 60 могут стать неразличимыми.
При этом основную работу со структурой книги выполняет openpyxl; XML не вычисляет формулы.
Строка `46271` и число 46271 с форматом General — `DATE_NUMERIC_AMBIGUOUS`.
Не угадывать Unix timestamp, `YYYYMMDD`, номер заявки или serial по величине числа.

Не принимать: двухзначный год; дата без года/дня, в том числе текст только из четырёх цифр года;
смешанный разделитель; относительные даты
«вчера/сегодня»; две даты или диапазон; нечитаемый текст; текстовые даты с несогласованным
комментарием; bool/список/неизвестный тип. Для известных неполных компонентов — `DATE_INCOMPLETE`,
двух дат — `DATE_MULTIPLE`, голого числа — `DATE_NUMERIC_AMBIGUOUS`, остального — `DATE_UNSUPPORTED`.
Если разрешённая форма разобрана, но компоненты невозможны, всегда `DATE_INVALID`.
`09/03/2026` не является проблемой неоднозначности в этой версии: DMY явно задан заказчиком.
`12/31/2026` → `2026-12-31`: DMY невозможен, MDY однозначно существует (DEC-23).

нормализованный полный ФИО; именно полный ФИО участвует в сравнении дублей.
Неизвестные компоненты, два имени и другие неоднозначные слова это исключение не расширяют.

Не раскрывать инициалы в отдельном поле: NAME_INCOMPLETE. В группе допускается
выбрать подтверждённое полное имя другой строки по DEC-31, без угадывания инициала.
Слово с однозначной ролью фамилии/отчества,
но без имени — NAME_NOT_FIRST. Неизвестное написание — NAME_UNKNOWN (не доказательство
недействительности человека). Пересечение ролей, несколько имён или несколько допустимых
назначений с разными положениями FIRST_NAME — NAME_AMBIGUOUS. При этих кодах весь raw сохраняется;
исключение частичного результата DEC-29 описано выше.

Для 2–3 компонентов перечислить назначения с ровно одним FIRST_NAME,
не более одной LAST_NAME и одной PATRONYMIC. Неподтверждённую FIRST-роль из одного
russiannames не использовать, но его подтверждённые LAST/PATRONYMIC сохранять
как кандидатов в контексте. Проверенные исключения DEC-25 сохраняют силу.
Автоматическое извлечение разрешено, если во всех допустимых назначениях FIRST_NAME
принадлежит одному компоненту. Например, «Степанова Вера»: роль «Степанова» может
быть LAST_NAME или PATRONYMIC, но личное имя во всех назначениях — «Вера».
В components роли такого слова записать через `|`, в аудите — все назначения.
Одиночные неоднозначные слова не подтверждаются этим контекстным правилом.
Неизвестный компонент и принудительно неоднозначные Ким/Али/Ли/Нгуен/Петрович
по-прежнему требуют проверки (исключение DEC-29 сохраняется). Сокращённое
имя канонизируется как личное имя; фамилия/отчество из raw не стираются: все исходные
компоненты, полный нормализованный ФИО и действие NAME_COMPONENTS_EXTRACTED в аудите.
Дефисные личные имена — единый компонент; дефис с пробелами остаётся ошибкой.
Не переставлять компоненты исходного ФИО. Сравнение дублей использует полный
набор нормализованных компонентов по DEC-33, чтобы одинаковое личное имя не скрывало разные фамилии.
Латиница и спорный регистр продолжают сохраняться для проверки по DEC-13/14.

Пустое имя — `NAME_MISSING`. Допустимая непустая строка содержит буквы Unicode,
комбинирующие знаки, Unicode-пробелы, дефисы `-‐‑‒–—`, апострофы `'’` или точки инициалов.
Хотя бы одна буква обязательна. Точки допустимы только после однобуквенных инициалов;
нет пустых дефисных/апострофных частей. Цифры, скобочные роли, email, emoji,
невидимые управляющие символы и прочая пунктуация — `NAME_INVALID`, кроме DEC-34.
В рабочей копии U+200B/U+FEFF удаляются только в начальном/конечном непрерывном
блоке этих знаков каждого слова, разделённого Unicode-пробелами. Позиции в исходной
NFC-копии сохраняются действием NAME_INVISIBLES_REMOVED. Внутри слова, bidi и
прочие невидимые символы не удаляются. Поле из одних этих знаков остаётся NAME_INVALID.

Перед обработкой имени вычислить `unicodedata.normalize("NFC", raw)` для рабочей копии.
Исходный текст и байты не изменяются. NFC применяется также к ключу сравнения имени в дублях,
включая имя, оставленное без изменения для ручной проверки. NFKC/NFKD не применять.

После определения пропуска: если имя содержит любую букву Unicode с именем символа LATIN,
всё поле оставить буквально и добавить NAME_LATIN_SCRIPT. Регистр, пробелы и пунктуация
такого имени автоматически не меняются. При смеси с кириллицей дополнительно NAME_MIXED_SCRIPT.
Это правило не означает «нет имени» и не доказывает ошибку человека: это диагностика по решению заказчика.
Для сравнения таких значений разрешён только NFC, без casefold/title или перестановки частей.

Внутренний спорный регистр кириллической буквенной части (например, `лИ`) даёт NAME_CASE_REVIEW:
всё поле оставить буквально для ручной проверки. Однозначные формы полностью строчными,
полностью прописными или с одной первой прописной разрешены. «ПАВЛОВА анастасия»
преобразуется в «Павлова Анастасия»; `McDONALD John` и `de Gaulle` остаются как есть.

Для допустимого имени без указанной диагностики:

1. Trim, все последовательности Unicode-пробелов заменить одним обычным пробелом.
2. В каждой буквенной части, отделённой пробелом/дефисом/апострофом/точкой инициала,
   первая буква — прописная, следующие — строчные; комбинирующие знаки остаются.
3. Сохранить вид дефиса/апострофа, буквы, ё, порядок частей и наличие инициалов.
4. Не дописывать фамилию/отчество, не переставлять имя и фамилию, не исправлять орфографию,
   не транслитерировать. «Сёмен» остаётся «Сёмен», даже если кажется опечаткой.

Кириллица и латиница в одной ячейке считаются риском подмены: `NAME_MIXED_SCRIPT` и NAME_LATIN_SCRIPT,
поле целиком остаётся исходным. Другие Unicode-алфавиты допустимы по общим правилам;
не требовать только русского имени. Регистр других алфавитов меняется только средствами Unicode.
Unicode-правила регистра иногда увеличивают длину (`ß` → `SS`): не обрезать значение;
проверять итоговый предел ячейки и фиксировать преобразование в аудите.

Неподдерживаемое имя не «чинить частично», например, нельзя превратить `иван123` в `Иван`.
Синтаксическая корректность имени не подтверждает его роль. Роли проверяются по
локальным справочникам и исключениям DEC-25; McDonald сохраняется с NAME_LATIN_SCRIPT.
Имя без фамилии допустимо при подтверждённой роли FIRST_NAME. «Ли» синтаксически
допустимо, но его роль неоднозначна; требуется проверка по DEC-25.

## 9. Источник

Копировать буквально, включая регистр, пробелы, неизвестный источник, пустоту и числовое значение.
Не ограничивать источники четырьмя значениями легенды и не маппить tg→telegram.
Формула/Excel-ошибка не исполняется и диагностируется по общему правилу.
В выходных представлениях строка, начинающаяся с `=`, `+`, `-`, `@`, записывается как текст,
а не активная формула. Нельзя добавить апостроф в само значение и считать его сохранённым:
нужно явно установить строковый тип ячейки.

## 10. Дедупликация и конфликты

Сначала анализируются **все** поля **всех** строк. Затем строки группируются по `canonical_phone`.
Телефон без успешного canonical не имеет ключа; отсутствующие/испорченные одинаковые значения не объединяются.
PHONE_EXTRA_CONTEXT не отменяет ключ: номер распознан, контекст диагностируется отдельно.
Для каждого успешного телефона представителем является строка с минимальным физическим
номером на выбранном листе. Сортировать даты, оценивать полноту или менять представителя запрещено.

Представитель не меняется. Для его рабочего результата Имя, Телефон и Дата выбираются
независимо: первое по физическому порядку значение с canonical и без кодов данного
поля. Если такого значения нет, поле не подтверждено, группа в Данные не допускается.
Источник сохраняется от первой строки буквально; его формула/ошибка блокирует допуск.
Выбранные поля сохраняются отдельно от анализа исходных строк; каждый донор и правило
записаны в GROUP_RESOLUTION. Дубли исчезают только из Данных; в Оригинале и Аудите
остаётся каждая запись, а дефекты дублей остаются в Проблемах.

Сравниваются только поля с canonical. Для дат сравнивается ISO-дата, для имён —
FIRST_NAME и мультимножество остальных компонентов: NFC, casefold, ё→е только
в сравнении внутри одного телефонного ключа. Порядок компонентов не влияет на сравнение.
Одинаковое личное имя и совпадающие либо дополняющие друг друга остальные компоненты
(один набор — подмножество другого) совместимы. Разные фамилии с одним именем конфликтуют.
Сравнить все пары: короткое «Иван» не должно скрыть конфликт «Иван Иванов» / «Иван Петров».
Исходные написания не подменяются ключом сравнения. Missing/битое поле не создаёт
конфликт двух подтверждённых значений, но его собственный код остаётся проблемой.

Если в группе есть несовместимые подтверждённые имена/ФИО или разные canonical даты, каждому участнику группы добавить
`DUPLICATE_NAME_CONFLICT` / `DUPLICATE_DATE_CONFLICT` соответственно, включая представителя.
Причина содержит все варианты и их исходные row_id. Даже два совпадающих участника группы
получают конфликт, если третий отличается. Проблемы фиксируются **одной строкой отчёта на row_id**
со всеми кодами; порядок кодов и вариантов стабильный.
Конфликты не блокируют итог с подтверждёнными полями (DEC-32): в Данных первая
подтверждённая версия, в Проблемах/Проверить все участники и расхождения.

Отличие только Источника не создаёт проблему. Аудит перечисляет все источники буквально
и связи дублей, первая запись сохраняет первый Источник. Идентичные после нормализации дубли
без иных дефектов не попадают в Проблемы, но всегда имеют аудит `DUPLICATE_LINKED`.

| ID | Сценарий | Данные | Проблемы |
|---|---|---|---|
| DUP-01 | Один телефон, всё идентично | Первая | Нет |
| DUP-02 | Разные формы одного телефона/имени/даты | Первая, стандартизированная | Нет |
| DUP-03 | Один телефон, отличается только источник | Первая с первым источником | Нет; источники в аудите |
| DUP-04 | Один телефон, разные имена | Первая подтверждённая версия, если все поля проверены | Все участники группы, конфликт имени |
| DUP-05 | Один телефон, разные даты | Первая подтверждённая версия, если все поля проверены | Все участники группы, конфликт даты |
| DUP-06 | Первая проблемная, следующая полнее | Подтверждённые поля группы; первый представитель | Исходные дефекты и подтверждённые конфликты |
| DUP-07 | Две одинаковые строки без телефона | Нет | Обе, не объединять |

## 11. Выход: один XLSX, ровно пять листов

### 11.1 Данные

Колонки строго **Имя, Телефон, Дата заявки, Источник**, без дополнительных технических колонок.
Исходный порядок представителей с подтверждёнными итоговыми полями группы.
Выбранные поля должны быть без кодов, с canonical имени, телефона и даты.
Конфликты и ошибки других исходных значений не блокируют допуск по DEC-31/32.
Пустой источник допустим по DEC-10. Проблемные значения
и пустые внутренние записи сохраняются в «Проблемах», «Оригинале», «Аудите», «Проверить».
Строка не теряется при отсутствии в рабочем листе. Ошибки/формулы представлены безопасным
буквальным текстом в отчётах с исходным типом в метаданных. Дубли в «Данные» не попадают.

### 11.1.1 Проверить

Пятый лист, после «Аудита». Колонки: **Имя, Телефон, Дата заявки, Источник, Лист входа,
Строка входа, Что не так**. Первые четыре колонки — исходные значения, без перестановки
или сокращения ФИО; формулы и ошибки — безопасный текст. Одна строка на проблемную исходную
запись, включая проблемные дубли; все причины перечислены коротко на русском, без JSON,
технических row_id и ссылок на куски аудита. Нулю проблем соответствует только заголовок.

### 11.2 Проблемы

Колонки:

`row_id`, `Лист входа`, `Строка входа`, `Строка в Данных`, `Представитель row_id`, `Статус`,
`Коды`, `Описание`, затем четыре пары `Имя исходное/Имя результат`,
`Телефон исходный/Телефон результат`, `Дата исходная/Дата результат`, `Источник исходный/Источник результат`.

Статус: `REPRESENTATIVE` / `UNGROUPED` / `DUPLICATE`. У дубля собственная «Строка в Данных» пустая,
«Представитель row_id» указывает на первую строку группы. У представителя ссылка на самого себя;
у строки без ключа тоже на себя. Список отсортирован по исходному номеру, а не по серьёзности.
`Коды` — стабильный уникальный список, разделённый `;`; `Описание` — русские сообщения
с полем и необходимыми деталями. Без проблем создаётся лист с заголовком и без записей.

Одна строка может иметь несколько причин, но её не нужно размножать на каждый код.
Технические ошибки файла (`SCHEMA_INVALID`, IO и т. п.) не выдаются за строковые проблемы:
при них итоговый файл не публикуется.

### 11.3 Оригинал

Колонки: `row_id`, `Лист входа`, `Строка входа`, **Имя, Телефон, Дата заявки, Источник**,
`Метаданные ячеек JSON`.

Все записи входного диапазона ровно один раз и в исходном порядке. `row_id` —
`s{index}:r{physical_row}`, например `s1:r2`; index — 1-based индекс листа в исходной книге.
Raw строки копируются буквально, формулы и ошибки — буквальным текстом. В JSON для каждой
ячейки: координата, исходный OOXML-тип, raw XML value/formula, декодированное значение,
тип Python, style_id, number_format, сведения о date epoch, target/location/display/tooltip
гиперссылки при наличии. Телефон из target/location не извлекается: используется только
значение ячейки (DEC-17). Числа сериализуются без
дополнительной потери точности; исходная лексическая запись берётся из XML.

Читаемый Оригинал не обещает копирование форматирования/картинок/связей книги. Побайтное
сохранение полной книги, включая остальные листы, оформление и скрытые данные, даёт Аудит.
Если JSON превышает 30 000 символов, в ячейке хранится ссылка на части `CELL_METADATA_CHUNK`
в Аудите; ничего не обрезается.

### 11.4 Аудит

Общий формат колонок:

`record_kind`, `row_id`, `input_cell`, `output_row`, `representative_id`, `field`,
`rule_id`, `old_value_json`, `new_value_json`, `details_json`, `chunk_index`, `chunk_payload`.

Виды записей:

| record_kind | Содержимое |
|---|---|
| RUN | spec-version, код/версия ПО, имя входа, SHA-256, размер, лист, epoch, счётчики |
| ROW | По одной записи судьбы на каждый row_id: представитель/дубль/без ключа |
| FIELD_CHANGE | Каждое фактическое изменение поля с правилом, старым/новым типизированным значением |
| GROUP_RESOLUTION | По одной записи на телефонную группу: выбранные поля, доноры row_id/ячейка, canonical/display, правило выбора, допуск, конфликтные коды |
| NAME_INVISIBLES_REMOVED | Исходник, рабочая копия, позиции и кодовые точки удалённых U+200B/U+FEFF на краях слов |
| NAME_ROLE_EVIDENCE | Возможные исходные роли одиночного слова из закреплённого справочника russiannames; причина ручной проверки по DEC-35 |
| PHONE_CONTEXT_EXTRACTED / DATE_TIME_PRESERVED | Извлечённая часть и весь оставшийся комментарий/время |
| FIELD_ISSUE | Все коды полей, даже на исключённых из Данных дублях |
| DUPLICATE_LINKED | Ссылка дубля на представителя и варианты источников |
| DUPLICATE_CONFLICT | Все варианты имён/дат и ссылки на участников |
| INPUT_CHUNK | Побайтный исходный XLSX, Base64 частями |
| CELL_METADATA_CHUNK / VALUE_CHUNK | Длинные сериализованные значения, без обрезки |

Сохранение исходного файла: Base64 кодируется из неизменяемого снимка входных байтов;
строка разбивается на части длиной **30 000 ASCII-символов** (кратно 4), индексы 0…K−1.
RUN содержит `encoding=base64`, chunk_count, byte_count и SHA-256. Склейка в порядке индексов
и `base64.b64decode(..., validate=True)` должны дать идентичный исходный файл.
Эта запись обязательна, даже если исходник будет сохранён рядом вручную.
Base64 — способ хранения, не шифрование. После ручного редактирования/пересохранения результата
гарантия восстановления требует повторной проверки хеша.

Длинные JSON разбиваются по 30 000 символов с `value_id`, индексами и полным SHA-256 UTF-8;
разбиение выполняется по символам Python и не изменяет текст. Прямые бизнес-значения,
которые не помещаются в допустимую ячейку XLSX, нельзя незаметно заменить ссылкой в Данных:
завершить `OUTPUT_LIMIT` до публикации, сохранив вход. Не рассчитывать на автоматическое
обрезание строк openpyxl до 32 767 символов.

Проверить заранее все пределы Excel, в том числе 1 048 576 строк на каждом листе
с учётом заголовка и аудита. Если результат не помещается в пять листов,
выдать `OUTPUT_LIMIT`; нельзя молча разделить на несколько файлов или отрезать хвост.

## 12. Инварианты сохранности и контроль результата

Пусть N — количество исходных записей, R — число групп с успешным телефоном,
U — число строк без однозначного телефона, D — число непервых записей в телефонных группах.

Обязательные равенства и проверки:

* `N = R + U + D`, `len(Оригинал) = N`. Пусть C — число представителей с подтверждёнными
  итоговыми полями по DEC-31/32; `len(Данные) = C`, `C <= R`. Остальные записи доступны в исходном реестре.
* `len(Проверить) = len(Проблемы)`; идентичный порядок проблемных исходных строк.
* Каждому входному row_id соответствует ровно один ROW; его disposition согласован с Данные.
* Инвентаризация row_id в Оригинале точно совпадает с входной, включая порядок и raw полей.
  Равное число строк не заменяет эту проверку: потеря строки и повтор другой могут взаимно скрыться.
* У всех дублей есть существующий представитель; циклов и ссылок на следующий дубль нет.
* Среди canonical_phone представителей нет повторов. Raw проблемный телефон не является ключом.
* Каждый проблемный входной row_id есть в Проблемах ровно один раз, даже если это дубль.
* Каждый изменённый field имеет FIELD_CHANGE с rule_id; неизменённые значения сохраняют raw.
  Перед публикацией проверяются также точное старое/новое значение и координаты FIELD_CHANGE,
  полные метаданные Оригинала (включая части JSON), детали ROW, единственность и содержимое
  DUPLICATE_LINKED, исходные/обработанные поля Проблем. Проверка наличия кода/ID недостаточна.
* GROUP_RESOLUTION единственен для каждого представителя с телефоном; проверяются
  все доноры, их минимальный порядок, группа, ячейки, значения, правила и допуск.
* Восстановленные байты входа имеют исходный размер и SHA-256.
* Исходник до/после запуска неизменен; другой существующий output не изменён.

Полнота исходных строк и восстановление входа требуются на **100%**. Цель валидности:
100% полей, объявленных успешно распознанными, соответствуют контракту. Доля проблемных
исходных строк — `P/N` (при N=0 выводить N/A), а не «количество причин / количество строк».
Доля дублей D/N описывает вход; повторов успешного телефона в Данных — ноль.

Детерминизм проверяется по значениям, row_id, решениям и причинам. ZIP-время создания XLSX
и необязательное время RUN не обязаны давать побайтно одинаковый результат двух запусков.
Идемпотентность значений требуется для телефона, даты и однозначного одиночного имени.
Контекстное извлечение имени не сохраняет однозначность при потере ФИО: «Иван Иванов»
→ «Иван», но отдельное «Иван» по DEC-35 требует проверки. Свидетельства сохраняются
в Оригинале/NAME_COMPONENTS_EXTRACTED; идемпотентность имён без контекста не заявляется.
Повторная обработка целого
многолистового результата без явного `--sheet Данные` не требуется и не должна дублировать аудит.

## 13. Коды диагностики

| Код | Когда |
|---|---|
| PHONE_MISSING | Нет телефона или маркер отсутствия |
| PHONE_INVALID | Повреждённый/короткий/длинный/буквенный номер, неподдержанный тип |
| PHONE_UNSUPPORTED_PREFIX | Явный префикс вне согласованного формата |
| PHONE_MULTIPLE | Несколько разных полных телефонов в одной ячейке |
| PHONE_CONTEXT_UNSAFE | Чужой идентификатор, буквенное примыкание, непонятная числовая привязка |
| DATE_MISSING | Нет даты или маркер отсутствия |
| DATE_INVALID | Календарно невозможная дата, некорректное время/offset, запрещённый Excel serial |
| DATE_INCOMPLETE | Нет дня/месяца/полного года, только время |
| DATE_UNSUPPORTED | Нераспознанный формат, буквы вместо цифр, несогласованный текст |
| DATE_NUMERIC_AMBIGUOUS | Голое число/цифровая строка без надёжной Excel-метаинформации |
| DATE_MULTIPLE | Несколько дат или интервал |
| NAME_MISSING | Нет имени или маркер отсутствия |
| NAME_INVALID | Цифры/посторонние символы/неподдержанный тип |
| NAME_MIXED_SCRIPT | Смесь кириллицы и латиницы |
| NAME_LATIN_SCRIPT | Латинские буквы: оставить поле целиком и проверить вручную |
| NAME_CASE_REVIEW | Спорный внутренний регистр: не менять, проверить вручную |
| NAME_UNKNOWN | Не удалось подтвердить личное имя; отсутствие в словаре не доказывает недействительность |
| NAME_AMBIGUOUS | Несколько ролей/личных имён; недостаточно данных для уверенного выбора |
| NAME_NOT_FIRST | Фамилия/отчество без личного имени |
| NAME_INCOMPLETE | Только инициалы вместо полного имени |
| CELL_NUMERIC_INVALID | Неконечная числовая лексема XML, сохранённая буквально по DEC-26 |
| PHONE_EXTRA_CONTEXT | Телефон успешно извлечён, дополнительный текст/время/добавочный в аудите и проблемах |
| FIELD_FORMULA | Формула в любом поле; не вычислять |
| FIELD_EXCEL_ERROR | Excel error cell в любом поле |
| DUPLICATE_NAME_CONFLICT | Разные имена в телефонной группе |
| DUPLICATE_DATE_CONFLICT | Разные даты в телефонной группе |

Диагностические коды NAME_LATIN_SCRIPT/NAME_CASE_REVIEW и PHONE_EXTRA_CONTEXT имеют severity=diagnostic,
входят в Проблемы и сохраняют различие с ошибкой извлечения. NAME_MIXED_SCRIPT — дополнительный
диагностический риск, а не отсутствие имени. В одном поле основной код выбирается по правилам анализатора, но проблемы разных полей
и конфликтные коды дедупликации накапливаются. Сортировка: поля в порядке входного контракта,
потом NAME_CONFLICT, DATE_CONFLICT. Общий FIELD-код с разными field не теряет детали в описании.
Пустое имя/телефон/дата одновременно даёт три кода, а не только первый.

## 14. CLI обработчика и восстановление

```powershell
python normalize.py --input files/zayavki.xlsx --output result/zayavki_result.xlsx
python normalize.py --input files/zayavki.xlsx --output result/zayavki_result.xlsx --sheet Заявки
python restore.py --input result/zayavki_result.xlsx --output restored/zayavki.xlsx
```

Оба выходных пути обязательны; новая директория создаётся при необходимости. `--force` и
перезаписи нет. Совпадение input/output, путь к существующему файлу, symlink/hardlink на исходник
или существующий результат — отказ до записи. Корректно обрабатывать пробелы и кириллицу в путях.

Ограничения ресурсов: `--max-input-bytes` (по умолчанию 104857600),
`--max-uncompressed-bytes` (536870912), `--max-rows` (1048575, только normalize).
Превышение — exit 5. Не более 10000 ZIP-частей; XML DTD/ENTITY запрещены.
План технических решений записан до реализации в `docs/IMPLEMENTATION_PLAN.md`.

Обработка: прочитать снимок байтов → проверить контейнер/схему → анализировать → дедуплицировать →
построить отчёт в памяти/временном файле → проверить инварианты и восстановление → опубликовать
новое имя через операцию без перезаписи. На Windows `os.rename` отказывает при существующем
назначении; на других ОС требуется операция с эквивалентной гарантией no-replace.
Проверка `exists()` + `os.replace()` не подходит из-за гонки и перезаписи.
При ошибке удалить только собственный проверенный временный файл; вход и старые результаты целы.

Exit codes:

| Код | Значение |
|---|---|
| 0 | Результат опубликован; проблем может быть любое количество |
| 2 | Ошибка аргументов, формата входа, схемы/листа/объединения |
| 3 | Ошибка чтения/записи, совпадение путей, существующий output |
| 4 | Не выполнен инвариант/хеш/неожиданная внутренняя ошибка |
| 5 | Пределы XLSX или явно настроенные ограничения ресурсов |

stdout: output path, spec-version, N, R+U, D, P и количество причин по кодам.
stderr: краткая причина технической ошибки, без публикации частичного результата и полного
содержимого пользовательских заявок. Не ставить exit=1 только из-за проблемных строк.

`restore.py` проверяет заголовки/виды audit-записей, отсутствие пропущенных/дублированных индексов,
Base64, размер и SHA-256, затем публикует восстановленный XLSX с тем же запретом перезаписи.
Итог восстановления должен совпадать с входным файлом **побайтно**, а не только по значениям.

## 15. Архитектура реализации

Структура Python-модулей реализована в пакете normalizer:

```text
normalize.py                 CLI → orchestrator
restore.py                   восстановление входа
normalizer/
  models.py                  RawCell, RawRow, FieldResult, RowResult, Issue
  reader.py                  OOXML snapshot, schema, sheet, typed raw
  phone.py                   кандидаты, контекст, структура
  dates.py                   whitelist formats, календарь, Excel epoch
  names.py                   тип/алфавит/пробелы/регистр
  deduplicate.py             первый представитель, доноры полей, связи, конфликты
  report.py                  пять листов, безопасный текст, аудит
  preservation.py            Base64, chunks, SHA-256, восстановление
  invariants.py              баланс, ссылки, валидация
  files.py                   временный файл, публикация без замены
  pipeline.py                последовательность обработки и восстановление
```

Основной цикл:

```text
snapshot = immutable_read(input)
rows = validate_and_read(snapshot, sheet)
processed = [analyze_all_fields(row) for row in rows]
groups = group_only_valid_canonical_phones(processed)
keep_first_representative_and_resolve_fields(groups, processed)
report = build_five_sheets(processed, snapshot, spec_version)
verify_invariants(report, processed, snapshot)
publish_without_replacing(report, output)
```

Python 3.11+; проверенный генератор работает на Python 3.14.5 с openpyxl 3.1.5
и et-xmlfile 2.0.0. Зависимости зафиксированы в `requirements.txt`. Для календаря, CLI, хешей,
Base64 и тестов используется стандартная библиотека. libphonenumber и dateutil не обязательны:
их permissive parsing нельзя подменять согласованными правилами. Никакой зависимости от сети
на этапе обработки. Чтение/анализ O(N + длина всех ячеек), группировка O(N), память O(N + размер входа).
Большие входы допускают потоковый reader/writer при сохранении порядка и всех инвариантов.

Программные ошибки не превращать в `PHONE_INVALID`: известные ошибки данных обрабатываются
локально, исключения инфраструктуры прерывают запуск. XML/ZIP должен проверяться на корректность,
не читать внешние entities/ссылки; настраиваемый предел распаковки даёт явный отказ, не усечение.
Поддержка размеров подтверждается измерениями в целевой среде, а не выдуманными SLA.

## 16. Предварительный генератор — реализован

Файлы: `tools/generate_data.py`, декларативный каталог `fixtures/scenarios.py`,
`tests/test_generator.py`. Генератор не читает пользовательский файл и не реализует очистку.
Эталонные ожидания записаны вручную; они не получены вызовом будущего нормализатора.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe tools/generate_data.py --output-dir generated/new-suite --mode suite
.\.venv\Scripts\python.exe tools/generate_data.py --output-dir generated/clean-1000 --mode clean --rows 1000 --seed 42
.\.venv\Scripts\python.exe tools/generate_data.py --output-dir generated/dirty-230 --mode dirty --rows 230
.\.venv\Scripts\python.exe tools/generate_data.py --output-dir generated/mixed-48 --mode mixed --rows 48
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

`--output-dir` обязан быть новым; существующий каталог не изменяется. `--rows` 0…100 000,
`--seed` целое, `--epoch` 1900/1904 (для одиночных файлов; suite включает оба независимо).
Перезапись запрещена; при ошибке нет частично опубликованного каталога.

Режимы:

* **clean**: ровно указанное количество корректных записей, уникальные строковые телефоны.
* **dirty**: ровно указанное количество строк; последовательно меняется одно поле по каталогу.
  «Грязные» включает и успешно исправимые, и проблемные примеры. Малый count не обещает весь каталог.
* **mixed**: каждая третья строка чистая, остальные используют индексированный сценарий.
  Этот режим моделирует смесь; полное покрытие обеспечивает dirty в suite.
* **suite**: clean, dirty (не менее всех 230 кейсов), mixed, duplicates,
  epoch_1900, epoch_1904, missing_header, duplicate_header, extra_header, merged,
  multiple_sheets, headers_only, empty_book, corrupt — **14 XLSX**.

Рядом создаются `manifest.json` с seed, исходными значениями, Excel-номерами строк,
ID сценария, ожидаемыми полями/кодами, ожидаемой судьбой дублей и SHA-256 каждого файла;
`cases.json` с полным каталогом. Для типов Excel JSON использует объект
`{"type": "number|datetime|serial|boolean|formula|error", "value": ..., "number_format": ...}`.
`expected` невалидного кейса означает сохранение raw, а не successful canonical.
С версии 1.1 у кейса явно есть `canonical`, `status`, `diagnostic_codes`, `problem_list`;
наличие кода PHONE_EXTRA_CONTEXT не исключает успешный canonical_phone и дедупликацию.
Для одного поля это не всегда полный oracle строки: остальные поля берутся из чистой основы,
а случайное совпадение телефона после подстановки может дополнительно создавать дубль.
При тестах полей каждый case проверяется изолированно; группа дублей проверяется отдельным файлом.

При 1904 ожидаемые serial-кейсы адаптируются в manifest: 2026-09-06 = 44809, serial 60 валиден.
У `cases.json` базовый каталог 1900; для конкретного XLSX приоритет имеют его labels в manifest.
Seed воспроизводит значения и метки, не обязательно байты ZIP. Синтетические телефонные строки
созданы для тестирования; совпадение с реальным номером не исключено и не проверялось.

`generated/spec-1.7-release-suite/` — демонстрационный набор 1.7 (результат проверки — README).
В `duplicates.xlsx`: 12 исходных строк → 4 проверенные строки Данных, 5 дублей;
7 первых/негруппируемых строк — это число представителей, а не допуск в Данные. Проблемы в исходных
строках 2/3/4/5/6/7/8/10; отдельная source-only группа в строках 12/13 — только аудит.
Строка 4 тоже имеет отличие источника, но входит в группу с конфликтом имени/даты:
поэтому все участники этой группы 2/3/4/5 присутствуют в Проблемах.

`generated/baseline/`, `generated/verified-v1/`, `generated/final-suite/` относятся к версии 1.0;
`generated/spec-1.1-suite/` и `generated/spec-1.2-suite/` относятся к предыдущим версиям;
Историческая приёмка 1.4 относится к `spec-1.4-suite`, 1.5 — к `spec-1.5-final-suite`,
1.6 — к `spec-1.6-final-suite`; актуальная 1.7 требует нового запуска. Старые наборы не перезаписаны.

## 17. Проверенные внешние источники и грязные данные

Проверка выполнена 2026-10-08. Источники не определяют бизнес-логику вместо заказчика.

1. [Government Data Quality Framework](https://www.gov.uk/government/publications/the-government-data-quality-framework/the-government-data-quality-framework)
   и [практическое руководство](https://www.gov.uk/government/publications/the-government-data-quality-framework/the-government-data-quality-framework-guidance):
   используются различия полноты, уникальности и валидности, заранее установленные правила
   качества и измерение результата. Наши инварианты и spec first — проектное применение,
   а не утверждение, что framework предписывает конкретную архитектуру Python.
2. [Google libphonenumber FAQ](https://github.com/google/libphonenumber/blob/master/FAQ.md):
   опубликованные кейсы букв в номере показывают риск permissive parsing. P36–37 используют
   краткий пример и адаптацию этого класса ошибок. Проверка диапазона не доказывает доступность.
3. [Python datetime](https://docs.python.org/3/library/datetime.html):
   календарь проверяется стандартной библиотекой.
4. [openpyxl: Dates and Times](https://openpyxl.readthedocs.io/en/stable/datetime.html):
   проверены две системы дат и проблема Excel 1900-02-29. Поэтому нужен raw XML serial,
   а не только datetime после высокоуровневого чтения.
5. [OpenRefine: Exploring data](https://openrefine.org/docs/manual/exploring):
   проверочные формы текстовых дат; D47 адаптирует короткий пример. Наша DMY-политика
   определяется заказчиком и не наследует эвристики OpenRefine.
6. [Реальный учебный dirtydata-каталог](https://github.com/paulbradshaw/cleaning/tree/master/dirtydata),
   опубликованный автором материалов об очистке данных.
   Проверен [Birmingham-FSA_TOCLEAN.csv](https://github.com/paulbradshaw/cleaning/blob/master/dirtydata/Birmingham-FSA_TOCLEAN.csv):
   6 338 записей, строковые даты со slash, 2 553 пустых AddressLine3. Нет blank RatingDate
   или внешних пробелов в BusinessName в проверенной версии: такие дефекты этому файлу не приписываются.
   SHA-256 исходных скачанных байтов: `d6f7e56e17c3fa61402a1580d305819b1e5d643ddb32e39309a8c679c47df479`.
   Проверен также [Goodreads DIRTY.csv](https://github.com/paulbradshaw/cleaning/blob/master/dirtydata/Dirty%20data%20Goodreads%20-%20Goodreads%20DIRTY.csv):
   11 120 записей, 2 publisher с внешними пробелами. В publication_date 4 550 значений
   распознаются только как DMY, 6 565 подходят и DMY, и MDY; ещё 5 значений не полная дата:
   строки CSV 2450/2451 = `2006`, 3711 = `2005`, 7698 = `2000`, 10524 = `1986`
   (нумерация с заголовком). Это проверенные плохие кейсы, а не придуманные ошибки.
   D49 включён в генератор на основе строки 2450: год без дня/месяца сохраняется с DATE_INCOMPLETE.
   Не обнаружено значений, подходящих только MDY; этому источнику не приписывается смешение локалей.
   SHA-256: `7bb20b9d46a60b370121bf458facff676e2cda1f761bf8a5018ce70fbdb9769d`.

Внешние CSV прочитаны и исследованы; целиком в проект не скопированы. Это не реальные заявки
с четырьмя колонками нашего контракта и не эталон правильных ответов. Генератор создаёт
самостоятельные синтетические кейсы соответствующих классов. Полный текст или большие
фрагменты чужих наборов не распространяются; лицензия на их дальнейшее распространение не проверялась.

## 18. План приёмки и последовательность разработки

1. **Генератор до обработчика** — выполнено. Десять тестов проверяют реальные типы XLSX,
   покрытие всех меток dirty, уникальность clean, воспроизводимость, запрет перезаписи,
   обе epoch и целостность manifest. Это проверка генератора, не доказательство работы нормализатора.
2. **Сначала contract tests**: по каталогу проверить field_result, запрет угадывания и сохранение raw.
   Дополнить параметризацию всех месяцев/пустых маркеров/Unicode-пробелов до реализации модулей.
3. **Reader + preservation**: raw XML, схемы, типы, snapshot, ID строк, восстановление хеша;
   проверить serial 59/60/61, 0 в обеих epoch, дробные serial и time-only.
4. **Анализаторы полей**: телефоны с корректными границами, календарь, имена; каждый rule_id
   обязан иметь позитивный/негативный тест, где применимо.
5. **Дубли и отчёты**: exact, source-only, name/date conflicts, дефекты в позднем дубле,
   первая плохая строка, отсутствие телефона; сверить duplicates.xlsx с manifest.
6. **Интеграция CLI**: пять листов, баланс строк, restore SHA-256, существующий output,
   совпадение путей, symlink/hardlink, исключение в середине записи, гонка назначения,
   блокировка файла Excel, недоступный каталог, отсутствие частичного результата.
7. **Пределы и регрессия**: 0/1/48/1000/100000 строк, длинные значения, максимальная длина
   ячейки, chunk boundaries, превышение audit rows, все скрытые строки, пустые внутренние строки,
   переставленные колонки, два листа, повторный заголовок, формулы и безопасный текст.
8. **Сдача**: скрипты, краткая инструкция, обработанный реальный input при его предоставлении,
   результат одного XLSX и его список проблем, полный экспорт сессий AI, 5–7 строк пользователя
   о процессе, версии зависимостей. Отчёт о реальном запуске не выдумывать, если input отсутствует.

Условие готовности обработчика: все нормативные сценарии и инварианты проходят;
нет молча выброшенных строк/полей и перезаписи; инструкция позволяет запустить CLI
на другом файле той же схемы. Изменения после приёмки сначала проходят обновление спецификации.
