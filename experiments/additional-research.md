## Дополнительное исследование: что ещё может сломать очистку XLSX

Я сопоставил твоё задание, материалы предыдущего исследования и документацию библиотек Python, Excel и инструментов тестирования.

В предоставленных материалах уже описаны 135 сценариев для телефонов, дат, имён и структуры файла. Отдельно исследованы ошибки вроде `lstrip("8")`, удаления кириллической буквы `О` из номера, неправильной интерпретации Excel serial 60 и некорректного применения `str.title()`. Повторять их как новые находки не имеет смысла.

Главный дополнительный риск — не ошибка распознавания отдельной ячейки, а ситуация, когда каждая функция по отдельности работает правильно, но весь процесс повреждает, пропускает или неправильно объединяет данные.

Поэтому я бы расширил испытания до трёх независимых уровней:

1. Содержимое: корректно ли программа распознаёт телефон, дату и имя.
2. Структура XLSX: правильно ли она читает реальные Excel-файлы с необычной внутренней структурой.
3. Сохранность: можно ли восстановить каждую исходную заявку после нормализации, дедупликации и записи результата.

При этом важно не менять уже утверждённые правила спецификации 1.0 ради того, чтобы пройти дополнительные тесты. Если новый сценарий обнаруживает пробел в правилах, он должен получить статус «требуется решение», а не автоматически превращаться в новую логику.

## 2. Как правильно построить тестирование

Я рекомендую использовать Specification-Based Testing + Property-Based Testing + Metamorphic Testing + Mutation Testing.

Это сочетание позволяет проверить не только заранее известные примеры, но и случаи, которые разработчик не предусмотрел.

Этап A. Эталонные тесты

Проверяем известные примеры с заранее утверждёнными результатами. Эталон определяется спецификацией, а не кодом программы.

Этап B. Генеративные и метаморфные тесты

Из правильных значений генерируем множество искажённых вариантов и проверяем, сохраняется ли смысл там, где это гарантировано.

Этап C. End-to-End XLSX

Создаём настоящие Excel-книги, запускаем программу из командной строки и затем независимо читаем итоговый XLSX.

Этап D. Проверки отказоустойчивости

Имитируем повреждённые файлы, ошибки записи, конфликт выходных путей и чрезмерные объёмы данных.

Этап E. Mutation Testing

Намеренно вносим ошибки в копию реализации и проверяем, обнаруживает ли их тестовый набор.

### Ключевой принцип: независимый эталон

Самая опасная ошибка тестирования — использовать одну и ту же логику для создания ожидаемого ответа и проверки результата.

Например, если генератор и очиститель оба ошибочно трактуют `09/03/2026` как американскую дату, тест может пройти успешно, хотя обе программы неправы.

Поэтому эталонный результат должен существовать до реализации парсера.

Для каждого сценария нужна запись следующего вида:

```

id: T-DATE-001
priority: P0
field: "Дата заявки"
raw_value: "09/03/2026"
raw_type: string

expected:
  status: normalized
  value: "2026-03-09"
  preserve_original: true

rule: "DMY, SPEC 1.0"

```

Для неоднозначного кейса вместо предполагаемого нормализованного значения фиксируется `policy_required`, а тест не попадает в категорию утверждённых успешных преобразований.

## 4. Самая важная проверка — отсутствие потерь

Проверки количества строк недостаточно.

Допустим, программа прочитала 48 строк и вывела 48 записей в аудите. Это ещё не доказывает, что все исходные строки сохранились: одну строку могли записать дважды, а другую пропустить.

Нужна проверка соответствия на уровне исходных записей.

Пусть:

- `N` — количество исходных заявок;
- `R` — количество представителей после дедупликации;
- `D` — количество исключённых дублей;
- `U` — количество остальных строк, которые не стали представителями.

Тогда в модели учёта из имеющейся спецификации должно выполняться:

\\[ N=R+D+U \\]

Но дополнительно нужно проверить, что идентификаторы всех исходных записей встречаются в общем аудите ровно по одному разу.

Пример проверки на исходных 48 заявках

# 48

Исходные

# 35

Представители

# 13

Остальные

35 + 13 = 48 — числовое условие выполнено

Нужно также проверить 48 уникальных исходных идентификаторов и соответствие исходным значениям

Числа 35 и 13 приведены для иллюстрации, не являются результатом обработки исходного файла.

Для исходных ячеек полезно сохранять тип, значение, координату, информацию о формулах и форматах дат. Их можно сериализовать по согласованным правилам и рассчитывать SHA-256.

Затем независимый тест сравнивает восстановленные данные с исходным инвентарём. Хеш всего XLSX здесь не подходит: библиотека может законно изменить внутреннюю ZIP-структуру при пересохранении, не изменив сами данные.

## 5. Тестировать не случайный мусор, а осмысленные мутации

Библиотека Hypothesis умеет генерировать пограничные случаи и сокращать найденный сбой до минимального воспроизводимого примера.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub



Но для этого задания просто генерировать случайные Unicode-строки малоэффективно: почти все они окажутся невалидными.

Полезнее строить генератор мутаций вокруг гарантированно корректного исходного значения.

Например, телефон `+79174005219`. От него генерируются варианты с разрешёнными разделителями, затем варианты с неразрешёнными символами, лишними цифрами, числами в комментариях и изменёнными типами Excel-ячеек.

Свойства, которые стоит проверять:

| Свойство                  | Обязательная проверка                                                                   |
| ------------------------- | --------------------------------------------------------------------------------------- |
| Идемпотентность           | Повторная нормализация уже нормализованного поля не меняет его                          |
| Сохранение смысла         | Разрешённое изменение форматирования телефона не меняет 10 национальных цифр            |
| Запрет догадок            | Невалидное значение не превращается в произвольное валидное                             |
| Независимость строк       | Добавление одной строки с другим телефоном не меняет результаты существующих строк      |
| Устойчивость дедупликации | Для каждого телефонного ключа остаётся один представитель, вся группа доступна в аудите |
| Полнота диагностики       | Любая непригодная строка получает предусмотренный статус и сохраняется                  |
| Детерминизм               | Один и тот же вход при одинаковой версии правил даёт одинаковые логические результаты   |

Дополнительно можно использовать Stateful Testing: библиотека будет генерировать не только значения, но и последовательности операций над тестовым набором. Например: добавить запись, добавить дубль, поменять порядок строк, снова нормализовать и проверить инварианты.&#x20;

### Проверка самого качества тестов

Здесь особенно полезен mutmut.

Он вносит небольшие изменения в код, чтобы проверить, способны ли тесты обнаружить дефект.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

boxed/mutmut: Mutation testing system · GitHub



Например, намеренно сломать программу так, чтобы она удаляла все ведущие восьмёрки вместо одной, меняла день и месяц местами, выбирала последний дубль вместо первого или переставала записывать одну категорию проблемных строк.

Если тесты после такого изменения остаются зелёными, значит соответствующая часть тестового набора недостаточна.

Для создания тестовых XLSX я бы использовал два независимых способа: обычную генерацию библиотекой XlsxWriter/openpyxl и точечное изменение XML внутри подготовленного ZIP-архива. Второй способ нужен для структур, которые нормальный Excel-генератор не создаст.

При этом повреждённые файлы и ресурсные стресс-тесты нужно запускать отдельно от обычных unit-тестов, с ограничением времени, памяти и размера распакованных данных.

## 7. Когда можно считать программу действительно проверенной

Предлагаю следующие критерии приёмки:

| Критерий                          | Требование                                                                                    |
| --------------------------------- | --------------------------------------------------------------------------------------------- |
| Эталонные сценарии спецификации   | 100% совпадений с утверждёнными ожидаемыми результатами                                       |
| Новые P0-сценарии                 | 100% успешно пройдены                                                                         |
| Сохранность строк                 | 0 пропущенных или неучтённых исходных заявок                                                  |
| Ложные автоматические исправления | 0 на утверждённом негативном наборе                                                           |
| Неоднозначные данные              | Не угадываются, остаются доступными для проверки                                              |
| Структурные ошибки XLSX           | Нет публикации незаметно неполного результата                                                 |
| Повторяемость                     | Одинаковый вход и версия правил дают одинаковые результаты                                    |
| Массовые испытания                | Нет падений, незаметных пропусков или нарушения инвариантов в согласованных пределах нагрузки |
| Mutation Testing                  | Все специально внесённые критические дефекты обнаруживаются тестами                           |

Это предлагаемые критерии проекта, а не результаты уже выполненных тестов.

Ещё одно важное условие: не следует автоматически считать пройденным тест на повторный запуск всего конвейера, если выходная книга содержит дополнительные листы аудита и не соответствует входной схеме. Идемпотентность отдельных нормализаторов и повторная обработка целого файла — разные проверки.

## Итоговая рекомендация

Я бы не пытался получить уверенность в системе за счёт бесконечного увеличения количества грязных строк.

Лучше разделить проверку на доказательство корректного преобразования и доказательство отсутствия потерь. Первое контролируется эталонами и генеративными тестами, второе — независимым аудитом всех физических строк, проверками записанного XLSX и испытаниями на сбои.

Особенно полезно зафиксировать правило:

> Любое новое преобразование должно сопровождаться положительным тестом, отрицательным тестом против ложного распознавания и проверкой сохранности исходных данных.

Для этой задачи я считаю наиболее опасными оставшимися направлениями неверные границы чтения XLSX, ошибки выходной записи, дефекты генератора тестовых данных и недостаточно независимый контроль сохранности записей. Именно с них стоит начать расширение существующих 135 сценариев.

Для исследования публичных репозиториев дополнительное подключение GitHub MCP не требуется: нужные материалы доступны открыто. Если позднее понадобится проверять приватный репозиторий с реализацией, тогда подключение GitHub станет полезным.
