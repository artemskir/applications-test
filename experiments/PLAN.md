# План проверки дополнительного исследования

План зафиксирован до реализации стенда. Основа: `gap-research.md` и приложенный
заказчиком дополнительный текст. Проверки выполняются локально, без запросов к сайтам.

1. Сверить рекомендации с действующей спецификацией, отделить исторические замечания
   к версии 1.0 от актуальных пробелов. Исправления бизнес-правил применять только
   после ответа заказчика, затем обновлять каталог и генератор.
2. Создать настоящие XLSX и изменения ZIP/XML: неверный dimension, повторяющиеся
   ZIP-имена, повреждённый CRC, чужой ZIP; проверить наблюдаемое поведение openpyxl.
   Экспериментальный валидатор контейнера не считать готовым входным адаптером.
3. Проверить типы и метаданные: bool, Excel error, формула, буквальный текст с `=`,
   tel-гиперссылка, DataValidation, merged cells, rich text, управляющие символы.
4. Проверить действующий генератор: отказ при существующем результате, ошибка
   сохранения, аварийное завершение и два одновременных запуска в один каталог.
   Источники и уже созданные артефакты не перезаписывать.
5. Проверить методологию: независимые календарные ожидания, весь набор часов
   комментария, инвентаризация идентификаторов строк вместо одного счётчика,
   перестановки уникальных записей и дублей. Модель дедупликации — только модель,
   её результаты не доказывают работу отсутствующего обработчика.
6. Целенаправленно внести несколько ошибок в копии функций и показать, какие
   контрольные примеры их обнаруживают. Не называть это полным mutation testing.
7. Измерить запись и чтение до 100 000 строк. Это наблюдение одной среды, не SLA
   и не проверка памяти будущего четырёхлистового результата.
8. Сохранить машинный отчёт, фикстуры, хеши; написать отчёт и README с реально
   выполняемыми командами. Отдельно перечислить проверки будущего обработчика.

Критерий стенда: ненулевой exit code при нарушенном контрольном ожидании; JSON
с отдельными `checks`, наблюдениями, ограничениями и отпечатками исходных документов.
Результаты библиотек не подменяют ожидаемые результаты спецификации.

Подтверждённые уточнения заказчика:

- Использовать только значение ячейки телефона; адрес tel-ссылки сохранять как метаданные.
- `вн.`, `доп.`, `*`, `;ext=` разрешают извлечь основной номер; весь контекст
  сохранять в аудите и проблемах. Пробел после `+` — допустимое форматирование.
- ISO datetime `YYYY-MM-DDTHH:MM` принимать; календарную часть сохранять без
  перевода в UTC, отброшенную временную часть записывать в аудит.
- Отдельный дефис в имени (`анна - мария`) остаётся ошибкой NAME_INVALID.
